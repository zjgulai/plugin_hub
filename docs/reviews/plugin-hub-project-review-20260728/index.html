Architecture & invariants

完整设计逻辑

主链路遵循“先保真、再统一、后推断、最终行动”的顺序，任何推断不得越过证据层。

05 / 15
01 / CONTEXT平台页面ASIN / thread / media
02 / CAPTURE独立扩展Amazon / Reddit / Instagram
03 / GATEAPI + 授权read/write key / allowlist / preflight
04 / ASSET单事务落库run + raw + canonical
05 / DERIVE关系与洞察signal / note / brief
06 / HISTORY不可变快照explicit migration / digest / trigger
07 / ACTIONVOC Hub复核 / 诊断 / 行动

不可破坏的项目不变量

  • 成功采集必须在一个 repository transaction 写入 collection_runs、raw_source_items、canonical_voc_units。
  • raw 是 append-only 业务证据；部署不得删除或重写它。
  • read-time 洞察不是历史；只有显式 0001_analysis_snapshots 与 snapshot API 创建的行才是历史。
  • 本地、fixture、生产只读、授权 live side effect 是不同证据等级。
  • Instagram 必须同时通过凭据、live-read 开关和 task authorization，且 production_write=false。

关键设计取舍

  • SQLite降低 P0 运维成本，但要求 WAL、busy timeout、备份和单写者所有权。
  • 平台独立扩展包隔离权限与商店版本，共享捕获、契约、UI 和后台。
  • 确定性洞察优先避免 provider 成本与幻觉；后续 LLM 只能润色/排序并保留 evidence refs。
  • Graph/API gate把“代码存在”“fixture 通过”“可 live read”“允许生产写”拆开。
  • 显式迁移仅负责快照历史，避免 startup create_all偷建历史表。

05 · API 安全与接入层FastAPI · read/write API key · TrustedHost · CORS · SSRF allowlist本地强基线

当前事实

  • 所有 /api router 统一依赖 require_api_access。
  • GET/HEAD 允许 read 或 write key，写操作只允许 write key。

  • 常量时间比较，secret 使用 Pydantic SecretStr。
  • Reddit/Instagram 外部 URL 先 allowlist，再限制 redirect/size。

  • 本地可显式 disabled；生产必须 required。
  • 通过 X-Plugin-Hub-Api-Key 传递。

下一迭代

06 · 数据资产、Schema 与 ETLrun/raw/canonical 单事务 · 平台保真 · SQLite WAL · hash/idempotency核心强 / DB 约束需深化

当前事实

  • 一个事务写 run、raw、canonical，异常 rollback。
  • 输入最多 2,000 raw，批次内应用层去重，extension hash 服务端复核。
  • FK、busy timeout、可选 WAL/FULL、文件 0600。

设计逻辑

  • raw 保真，canonical 统一，platform_extension 保差异。
  • 跨 run 重复可以代表不同时间采样；批次内重复不应存在。
  • idempotency key 冲突返回 409，不静默覆盖。

当前风险

  • raw/canonical append-only 主要靠应用约定，DB 无 UPDATE/DELETE trigger。
  • 核心表仍由 create_all 管理，只有 snapshot 是显式迁移。
  • 缺少批次唯一 index 的数据库级最后防线。

下一迭代

  • P0/P1：新增 baseline migration 与 raw/canonical immutability trigger。
  • 加 run 内唯一约束和复制库 dry-run。
  • 规模阈值：写锁/文件大小/查询时延达到门槛后再评估 PostgreSQL。

当前事实

设计逻辑

  • 失败不是裸字符串，要有 retry/terminal 语义。
  • API 与 CLI worker 共用 handler 和 DB 配置。
  • 配置状态不等于 capability ready。

当前风险

  • claim 先 SELECT 全表、再内存判断和 UPDATE/commit；多执行者无条件更新。
  • 顺序双 session 测试不能证明真正并发只认领一次。
  • 缺少队列深度、耗时、失败率、stale 次数指标。

下一迭代

  • P0：条件 UPDATE/CAS 或受控 BEGIN IMMEDIATE，并发 barrier 测试。
  • P1：任务事件表、dead-letter/replay、SLO 与告警。
  • 验收：N 个 worker 对 1 个 task 只有 1 个 side effect。
